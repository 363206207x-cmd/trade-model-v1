## 2. Executive Summary

The core V1 semantic chain is valid:

`rule-led analysis -> decision -> system execution suggestion -> manual user
position -> read-only monitoring -> manual close fact -> optional review`.

The current implementation preserves the two most important safety boundaries:

1. `ExecutionPlan != UserPosition`.
2. AI cannot replace the rule-layer base direction or authorize a trade.

However, the current Figma set cannot be treated wholesale as implementation
ready. The following remain material contract gaps:

- Complete evidence, all eight score details, and four explicit timeframe rows
  do not have one authoritative public read contract.
- AI role summaries exist, but normalized role-to-evidence provenance does not.
  Any claim that the UI is showing each role's "complete evidence" is false.
- Some dashboard queries can select a sibling execution plan by analysis
  identity. Plan values are safe only after exact plan/source validation.
- Manual position creation requires quantity and leverage, while `openedAt` is
  generated by the server. A UI that asks only for symbol, direction, opening
  price, and a user-entered opening time does not match the backend contract.
- External notification delivery is disabled by no-op publishers. Eligibility
  and audit records do not prove delivery.
- Telegram is an extension, not a current V1 product capability.
- AI call frequency and token budget are backend operational controls, not user
  settings.

Overall frontend contract status:

`PARTIAL_WITH_EXPLICIT_FAIL_CLOSED_GAPS`

- `GEMINI_REVIEW` - 冲突复核官
- `GROK_CHALLENGE` - 反方挑战官

| Capability | Backend reality | Frontend status |
|---|---|---|
| Three role identities | Present | `READY` |
| Role summaries/opinions | Present in decision/dashboard projections | `READY` |
| Current direction | Rule-led decision field | `READY` |
| Confidence/risk adjustment | Present in decision review result | `READY` |
| Conflict explanation | Present as review/challenge summary fields | `READY` |
| Normalized role-to-evidence IDs | Not present as an authoritative public contract | `FAIL_CLOSED` |
| Complete role-specific evidence inspector | Not provable from current public data | `FAIL_CLOSED` |
| AI voting/winner | Not part of the model | Forbidden |
| AI trade authorization | Not part of the model | Forbidden |

Required role boundaries:

- `GPT_FINAL` may show the final conclusion and the evidence summaries actually
  linked to the decision.
- `GEMINI_REVIEW` may show conflict, weakness, missing-condition, and
  maintain/adjust/downgrade information. It must not invent an independent
  trading direction.
- `GROK_CHALLENGE` may show external-event and counterargument information
  actually returned by the backend. It must not invent technical evidence.

Current contract violation:

- The mobile implementation and some Figma AI inspectors use wording equivalent
  to "complete role evidence." The data is role summary/reason content, not a
  normalized complete evidence graph. The copy must be downgraded to
  `当前角色观点` plus `完整证据关联尚未提供` until provenance exists.

AI is not a voting system. AI cannot bypass the rule layer, open a position,
change a real position, or trigger a trade.

## 7. Evidence and Scoring Contract Audit

### 7.1 Evidence

The analysis pipeline can produce evidence for:

- price structure;
- leverage;
- funding/capital flow;
- event;
- risk.

An evidence item can carry type, description/current condition, direction,
strength, confidence, source/provider/reference, and trace metadata. The normal
frontend read path does not expose an authoritative complete analysis-scoped
evidence chain; reduced/top-three summaries are the proven public behavior.

| Presentation | Status | Rule |
|---|---|---|
| Top evidence summary | `READY` | Label explicitly as a reduced summary |
| Supporting and opposing summary | `PARTIAL` | Show only returned records; show an empty state independently for each side |
| Full evidence chain | `FAIL_CLOSED` | `详细证据尚未提供` |
| Fabricated evidence examples | Forbidden | Do not use realistic sample content as live evidence |

### 7.2 Eight Scores

The analysis process defines:

1. trend structure;
2. funding/capital drive;
3. leverage risk;
4. liquidity quality;
5. sentiment temperature;
6. event impact;
7. macro environment;
8. overall credibility.

The current public score endpoint is not an authoritative persisted
analysis-scoped detail read. It can derive scores from a synthetic market
summary and therefore must not be used to claim historical/full score
traceability.

| Presentation | Status | Rule |
|---|---|---|
| Composite score projection | `READY` | Summary only |
| Reduced score briefs | `PARTIAL` | Clearly label the reduced set |
| Complete eight-score values | `FAIL_CLOSED` | Show each unavailable dimension as `待同步` or `--` |
| Ranking/trading signal inferred from missing scores | Forbidden | No inference |

### 7.3 Multi-Timeframe

The contract recognizes `4H`, `1H`, `15M`, and `5M`, with `5M` used as a
short-term risk/liquidity filter rather than the main trend. The current public
read does not provide one authoritative row per timeframe with complete
provenance.

Frontend status: `FAIL_CLOSED`.

Allowed display:

- returned aggregate convergence summary;
- four labeled rows containing `待同步` when row-level data is absent.

Forbidden display:

- invented timeframe directions;
- treating `5M` as the main direction;
- presenting sample values as live analysis.

## 9. User Position and Position Monitoring Contract Audit

### 9.1 User Position Creation

The real manual-open backend contract currently requires:

- asset symbol;
- side/direction;
- entry price;
- quantity;
- leverage;
- optional user stop loss;
- optional user take profit.

The server supplies the opening timestamp. A product form defined as only
symbol, direction, opening price, and a user-entered opening time is not aligned
with the implementation.

Frontend status: `PARTIAL`.

The UI must either:

1. collect the real required quantity and leverage fields and disclose that
   opening time is server-recorded; or
2. remain unavailable until the backend/product contract is deliberately
   changed.

It must not fake a successful position creation.

### 9.2 Monitoring Fields

| Monitoring field | Backend support | Frontend status |
|---|---|---|
| Asset | Yes | `READY` |
| Position direction | Yes | `READY` |
| Entry logic still valid | Yes | `READY` |
| Direction support | Yes | `READY` |
| Reversal status | Yes | `READY` |
| Risk level/flags | Yes | `READY` |
| Current suggested manual action | Yes | `READY`, information only |
| Last monitor time | Yes | `READY` |
| Exact user-position/plan identity | Yes in monitor result | `READY` |
| Persisted human-handling/acknowledgment history | No dedicated contract | `FAIL_CLOSED` |

The monitoring service reads and records an assessment; it does not mutate the
user position. Data-quality degradation may block a new decision or plan, but
must not delete an existing position or stop its monitoring. The frontend must
not show a direct data-quality impact on a monitor result unless that result
actually carries a linked field.

### 9.3 Position Lifecycle

```text
暂无持仓
  -> 用户手动录入并形成 OPEN
  -> 持续只读监控
  -> 风险升高 / 逻辑失效 / 方向反转（仍等待人工处理）
  -> 用户记录部分或全部平仓事实
  -> CLOSED
  -> 可选复盘
```

`triggered` is not an open position. Recording a manual close is not an exchange
close command. No automatic close or reversal is allowed.

## 10. Push Notification Contract Audit

The current V1 product Push boundary contains only two business sources.

### 10.1 Executable-Opportunity Review Notification

Source:

`validated ExecutionPlan + notification eligibility policy`

Allowed content:

- asset;
- current review state;
- execution-suggestion summary;
- Push Recheck entry.

The word "executable" is a compatibility status term, not authorization to
trade.

### 10.2 Position-Risk Notification

Source:

`UserPosition + PositionMonitor`

Allowed triggers:

- approaching take profit;
- risk escalation;
- entry logic invalidation;
- direction reversal.

Current backend limitation:

- notification eligibility/audit types exist;
- the dashboard position-risk inbox count is not a complete integrated delivery
  proof;
- external publishers/providers are no-op and return delivery-disabled status.

Frontend status: `PARTIAL_WITH_FAIL_CLOSED_DELIVERY`.

Forbidden V1 Push sources:

- ordinary price changes;
- ordinary score changes;
- ordinary AI result changes;
- ordinary data refreshes;
- all-market scan noise.

`SYSTEM_DATA_WARNING` exists as an operational notification type. It is not one
of the two product Push sources defined by this audit and must remain
operational/internal unless a later product contract explicitly adopts it.

## 11. Push Recheck Contract Audit

Opening a notification must perform a current review. Push Recheck is never
trading authorization.

| Product/legacy status | Canonical backend meaning | Required user-facing meaning |
|---|---|---|
| `VALID_EXECUTABLE` | `RECHECK_REVIEW_PASSED` | 当前重新确认通过，仅供人工复核 |
| `VALID_WAITING` | `RECHECK_REVIEW_WAITING` | 当前仍需等待条件 |
| `DRIFTED` | `RECHECK_DRIFTED_FROM_ENTRY_ZONE` | 已偏离原入场区 |
| `INVALIDATED` | `RECHECK_INVALIDATED` | 原建议已失效 |
| `RISK_BLOCKED` | `RECHECK_RISK_BLOCKED` | 风险阻断 |
| `CONFUSED_BLOCKED` | `RECHECK_CONFUSED_BLOCKED` | 冲突阻断 |
| `EXPIRED` | `RECHECK_EXPIRED` | 已过期 |

The backend retains internal review trigger/latest/log behavior, while raw
user-facing latest/log reads fail closed and the current product frontend has
no complete mobile Push Detail route. The Figma Push frame is a valid target
only when it:

- uses review-only wording;
- consumes the server-side source-specific projection;
- shows original/current private risk fields only for owner-scoped
  `POSITION_RISK`;
- never exposes Recheck/account/position risk or private reason fields through
  authenticated shared `OPPORTUNITY`;
- exposes information navigation only;
- never offers execute, buy, sell, order, close, or position mutation.

Raw user-facing latest/log/preview access by `pushId` is not a frontend data
source unless an authoritative source-domain and owner relation is available.
The current raw rows do not provide that relation, so those paths and the
legacy raw service latest/list methods fail closed. UI state must preserve
`READY`, `PARTIAL`, `ERROR`, `MISSING`, and `EMPTY`. Public `OPPORTUNITY`
states use public inputs only and remain unchanged by missing/invalid/private
Recheck state. Private `POSITION_RISK` states use the same authoritative
latest-monitor resolver for list and detail and never treat row existence as
`READY`.

Status: `PARTIAL`.
