# P287 Market-Read Request DTO Authorization Gate

P287 is a docs-only Scope Pack for PR #693 / Issue #692.

P287 closes P286 and decides whether the next package may implement a pure-data `MarketReadRequestDTO` Java skeleton. P287 itself does not implement Java, tests, DTOs, dashboard, schema, config, API, scheduler, market-read runtime wiring, scan output, score computation, Candidate workflow, Push execution, Readiness, point generation, or trading behavior.

## 1. P286 Closure Baseline

P286 merged as `c09a15c`.

P286 was docs-only / contract-only. P286 defined the future `MarketReadRequestDTO` field plan, safety defaults, source boundary, and DTO authorization gate. P286 kept Java blocked.

## 2. P287 Scope

P287 only defines:

- P286 contract closure;
- future `MarketReadRequestDTO` skeleton authorization scope;
- exact future DTO field freeze;
- future DTO targeted-test requirements;
- future Java authorization gate for P288;
- runtime market-read blocked status;
- score / Candidate / Push blocked status;
- Readiness / point generation blocked status.

P287 does not modify Java, tests, DTOs, dashboard, schema, config, API, service, controller, scheduler, mapper, repository, DB read/write, migration, runtime data, scan output, scan loop, score computation, Candidate production workflow, Push execution, Readiness, point generation, or trading path.

## 3. P288 Authorization Decision

P287 authorizes P288 to implement a `MarketReadRequestDTO` Java skeleton only if P288 remains a pure-data DTO skeleton with targeted tests only.

If P288 cannot remain inside this pure-data DTO boundary, the recommended next package after P287 must be another docs-only gate instead of Java.

P288 must not implement Spring wiring, service behavior, controller, endpoint, scheduler, mapper, repository, DB read/write, schema, config, dashboard, provider dependency, market data client dependency, runtime/live/external data read, scan output, real scan loop, production score, Candidate production workflow, Push execution, Readiness, point generation, or trading behavior.

## 4. Future DTO Field Freeze

The future `MarketReadRequestDTO` skeleton may contain only these fields:

- `symbol`;
- `requestId`;
- `sourceContractId`;
- `watchlistPoolProof`;
- `watchlistConfigVersion`;
- `requestedScanReason`;
- `requestedTimeframes`;
- `scanTimestamp`;
- `dataAvailabilityExpectation`;
- `stalePolicy`;
- `missingDataPolicy`;
- `riskBlockers`;
- `reviewOnly`;
- `notTradeInstruction`;
- `guardValidationStatus`;
- `blockingReasons`.

No additional fields are authorized in P288 without a later gate.

## 5. Future DTO Safety Defaults

Future `MarketReadRequestDTO` defaults must preserve:

- `reviewOnly=true`;
- `notTradeInstruction=true`;
- fail-closed stale policy;
- fail-closed missing-data policy;
- missing Watchlist Pool proof blocked;
- missing source contract blocked;
- missing timestamp blocked;
- missing timeframe blocked;
- blocking reasons preserved and expanded rather than discarded.

The DTO cannot upgrade an incomplete or blocked source into a valid market-read request.

## 6. Future DTO Source Requirement

Only a GuardValidator-approved `RealScanInputContractDTO` can source the future request.

Display Slots / 默认六币 cannot be scan universe or batch universe. Watchlist Pool remains the scan candidate boundary.

## 7. Future Targeted Tests

If P288 implements the DTO skeleton, targeted tests must cover:

- default `reviewOnly=true`;
- default `notTradeInstruction=true`;
- fail-closed stale policy;
- fail-closed missing-data policy;
- missing Watchlist Pool proof blocked;
- missing source contract blocked;
- missing timestamp/timeframe blocked;
- source limited to GuardValidator-approved `RealScanInputContractDTO`;
- blocking reasons preserved;
- no runtime dependency, client dependency, scan output, score, Candidate, Push, Readiness, point, or trading behavior.

Tests must remain targeted DTO tests only. They must not add production wiring or runtime market reads.
