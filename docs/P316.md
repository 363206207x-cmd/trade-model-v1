# P316 MultiTimeframe Numeric Point Contract Plan

## Purpose

P316 belongs to the Readiness / Point Mainline.

P316 is a docs-only MultiTimeframe contract plan after P315 `DATA_QUALITY_NUMERIC_POINT_CONTRACT_PLAN`.

It defines which multi-timeframe confirmation rules must exist before any future entry / stop / TP / RR numeric value can enter a review-only numeric point proposal.

P316 does not create Java DTOs, does not implement numeric point proposal, does not generate real entry / stop / TP / RR, does not connect dashboard runtime, does not connect external channels, and does not connect order / execution / auto-trading.

## What P316 Is Not

P316 is docs-only.

P316 does not raise Production Runtime Progress.

P316 does not mean MultiTimeframe Java DTO is complete.

P316 does not mean numeric point proposal is implemented.

P316 does not mean real entry / stop / TP / RR are complete.

P316 does not mean dashboard runtime integration.

P316 does not mean external push.

P316 does not mean order, execution, or auto-trading.

P316 does not allow direct order placement after merge.

## MultiTimeframe Contract Boundary

MultiTimeframe is the review-only gate that checks whether low-timeframe observations can participate in a future source-owned numeric point proposal without overriding higher-timeframe structure.

MultiTimeframe cannot generate entry / stop / TP / RR.

MultiTimeframe cannot replace SourceTrace.

MultiTimeframe cannot replace RuntimeKlineContext.

MultiTimeframe cannot replace DataQuality.

MultiTimeframe cannot replace Risk Action Guard.

It can only support:

- aligned review-only numeric proposal consideration;
- partial review-only consideration with missing reasons;
- `INCOMPLETE` when timeframe input is insufficient;
- `BLOCKED_FAIL_CLOSED` when conflict would induce trading action.

## Timeframe Roles

The future contract uses these timeframe roles:

- `4h`: structure, macro direction, and higher-timeframe conflict detection.
- `1h`: trend confirmation and key structural area confirmation.
- `15m`: primary execution observation timeframe and primary entry-zone reference timeframe.
- `5m`: short-term trigger, wick detection, and noise filtering.

Missing higher timeframe means lower-timeframe signals must not be upgraded into complete point proposals.

Lower timeframe may assist, but it must not override higher-timeframe conflict.

The 5m timeframe cannot decide trend reversal by itself.

## Required Timeframes

A future review-only numeric point proposal should normally have:

- primary timeframe, usually 15m for entry-zone review;
- at least one confirmation timeframe, usually 1h;
- higher timeframe, usually 4h, for conflict detection;
- lower timeframe, usually 5m, for trigger / wick / noise review.

If the higher timeframe is missing, the output must remain `INCOMPLETE` unless a later contract explicitly defines a safe degraded review-only path.

If only the lower timeframe exists, the output must remain `INCOMPLETE`.

## Entry MultiTimeframe Contract

Entry numeric point context must include:

- `primaryTimeframe`;
- `entryTimeframeSourceRef`;
- at least one `confirmationTimeframe`;
- no unresolved higher-timeframe conflict;
- `lowerTimeframeNoiseStatus` not trade-inducing;
- `wickConflictStatus` not unconfirmed wick;
- DataQuality contract passed;
- SourceTrace refs present;
- RuntimeKlineContext refs present;
- `riskActionGuardRef` present.

Entry multi-timeframe confirmation is not buy, long, open, or order instruction.

## Stop MultiTimeframe Contract

Stop numeric point context must include:

- `stopTimeframeSourceRef`;
- invalidation owning timeframe;
- higher-timeframe structural boundary context;
- lower-timeframe wick / noise review;
- gap / abnormal data context;
- liquidity / stampede review;
- `riskActionGuardRef`.

Stop multi-timeframe confirmation is not an automatic stop-loss order and not a market close suggestion.

## TP MultiTimeframe Contract

TP numeric point context must include:

- `tpTimeframeSourceRefs`;
- TP owning timeframe;
- higher-timeframe resistance / support / liquidity target context;
- `confirmationTimeframes`;
- no unresolved higher-timeframe conflict;
- liquidity / stampede review;
- `riskActionGuardRef`.

TP multi-timeframe confirmation is not an automatic take-profit order and not a sendable order.

## RR MultiTimeframe Contract

RR numeric review field must include:

- `entryTimeframeSourceRef`;
- `stopTimeframeSourceRef`;
- `tpTimeframeSourceRefs`;
- compatible timeframe hierarchy;
- no unresolved source timeframe conflict;
- `rrTimeframeConsistencyRef`;
- `missingReason` when any timeframe input is incomplete.

RR cannot be used alone as an open-position condition.

## Alignment And Conflict Rules

The future contract must use these states:

- `ALIGNED`: key timeframes have no directional conflict.
- `PARTIAL`: some timeframes support review, but confirmation is incomplete.
- `INSUFFICIENT`: required timeframes are missing.
- `CONFLICTED`: timeframes conflict.
- `TRADE_INDUCING_CONFLICT`: conflict could induce reverse, open, or chase behavior.
- `NOISE_ONLY`: signal comes only from lower-timeframe noise.
- `WICK_ONLY`: signal comes only from wick or pin-bar behavior.
- `STRONG_REVERSAL_UNCONFIRMED`: strong reversal lacks multi-timeframe confirmation.

State outcomes:

- `INSUFFICIENT` -> `INCOMPLETE`.
- `CONFLICTED` -> `INCOMPLETE`.
- `TRADE_INDUCING_CONFLICT` -> `BLOCKED_FAIL_CLOSED`.
- `NOISE_ONLY` -> `INCOMPLETE`.
- `WICK_ONLY` -> `INCOMPLETE`.
- `STRONG_REVERSAL_UNCONFIRMED` -> `INCOMPLETE`, or `BLOCKED_FAIL_CLOSED` when it could induce trade action.

## High-Timeframe Conflict

High-timeframe conflict must prevent lower-timeframe escalation.

If 15m or 5m suggests a point but 4h structure conflicts, the proposal must remain `INCOMPLETE` unless the conflict is resolved by a future contract.

If the high-timeframe conflict would induce immediate reverse, open, chase, or external push, the proposal must be `BLOCKED_FAIL_CLOSED`.

## Low-Timeframe Wick, Noise, And Strong Reversal

Low-timeframe wick or pin-bar behavior can identify review risk, but it cannot become trend reversal by itself.

5m signals can assist short-term trigger review but cannot override 1h or 4h context.

Strong reversal can be considered only when confirmed by higher timeframe, DataQuality, SourceTrace, RuntimeKlineContext, and Risk Action Guard.

Strong reversal does not mean direct reverse.

## MultiTimeframe That Can Only Support Missing Reason

MultiTimeframe can only support missing reason, not numeric values, when:

- only 5m signal exists;
- higher timeframe is missing;
- confirmation timeframes are missing;
- timeframe weights are missing;
- alignment status is unknown;
- higher-timeframe trend is unknown;
- lower-timeframe noise status is unknown;
- wick conflict is unknown;
- strong reversal status is unknown;
- source trace refs are missing;
- runtime kline context refs are missing;
- data quality context ref is missing;
- Risk Action Guard ref is missing.

## Review-Only Numeric Proposal But Still Not Executable

Future review-only numeric proposal consideration may happen only when:

- requested timeframes are present enough for review;
- primary timeframe is present;
- at least one confirmation timeframe exists;
- higher-timeframe conflict is resolved;
- lower-timeframe noise is not trade-inducing;
- wick-only signal is not used as trend reversal;
- SourceTrace refs pass;
- RuntimeKlineContext refs pass;
- DataQuality context passes;
- Risk Action Guard ref exists.

Even then, the output remains `reviewOnly = true`, `notTradeInstruction = true`, and `manualReviewRequired = true`.

It cannot become executable point generation, order intent, execution intent, or auto-trading.

## INCOMPLETE Conditions

Future numeric point proposal must stay `INCOMPLETE` when any condition is true:

- `multiTimeframeContextId` missing;
- `requestedTimeframes` missing;
- `availableTimeframes` insufficient;
- `primaryTimeframe` missing;
- `confirmationTimeframes` missing;
- `higherTimeframe` missing;
- lower timeframe only;
- `timeframeWeights` missing;
- `timeframeAlignmentStatus` unknown;
- `higherTimeframeTrendStatus` unknown;
- `lowerTimeframeNoiseStatus` unknown;
- `wickConflictStatus` unknown;
- `strongReversalStatus` unknown;
- `entryTimeframeSourceRef` missing;
- `stopTimeframeSourceRef` missing;
- `tpTimeframeSourceRefs` missing;
- `rrTimeframeConsistencyRef` missing;
- `sourceTraceRefs` missing;
- `runtimeKlineContextRefs` missing;
- `dataQualityContextRef` missing;
- `riskActionGuardRef` missing;
- high-timeframe conflict unresolved;
- only 5m signal exists;
- wick-only signal exists;
- strong reversal lacks confirmation.

`INCOMPLETE` may explain unavailable timeframe context but must not generate numeric values.

## BLOCKED_FAIL_CLOSED Conditions

Future numeric point proposal must become `BLOCKED_FAIL_CLOSED` when any condition is true:

- multi-timeframe context forged / untrusted;
- DataQuality hard threshold failed;
- SourceTrace / RuntimeKlineContext mismatch;
- high-timeframe conflict would induce immediate reverse;
- low-timeframe noise would induce entry;
- wick treated as confirmed trend reversal without confirmation;
- strong reversal treated as direct reverse;
- stampede confirmed;
- liquidity severely degraded;
- multi-timeframe context attempts to bypass Risk Action Guard;
- context implies buy / sell / long / short;
- context implies order intent;
- context implies execution intent;
- context implies auto-trading;
- external channel attempted before authorization.

`BLOCKED_FAIL_CLOSED` must never be rendered as a trade-ready numeric point.

## Risk Action Guard Integration

MultiTimeframe cannot bypass Risk Action Guard.

Risk Action Guard ref must enter MultiTimeframe context before future numeric point review.

High risk does not mean immediate stop.

High risk does not mean immediate reverse.

High risk does not mean immediate open.

Strong reversal does not mean direct reverse.

Wick / pin-bar behavior does not mean trend reversal.

Stampede state blocks opportunity push.

Degraded liquidity does not recommend one-shot market cutting.

Even complete MultiTimeframe context cannot become a trading action.

P316 moves the planning state from `DATA_QUALITY_NUMERIC_POINT_CONTRACT_PLAN` to `MULTITIMEFRAME_NUMERIC_POINT_CONTRACT_PLAN`.

It defines the minimum MultiTimeframe contract that future numeric point values must satisfy. It keeps all point work review-only, incomplete-safe, fail-closed, and blocked from executable trading semantics.
